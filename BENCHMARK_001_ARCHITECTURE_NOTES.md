# BENCHMARK-001 architecture notes (interim)

Status: interim evidence for issue #54. This is not the completed 22-job scorecard or final product recommendation. All hands-on data is synthetic; no password is recorded, no bank is connected, and no paid service was used.

## Actual Budget evidence checked on 2026-11-01

- The installed desktop client reported **v26.10.0**. The local browser server and browser client report **v26.10.0**. The owner completed the server's first-run password step in the browser; the secret is not recorded here. The server now reports online.
- The offline desktop client supports accounts, budgets, reports, schedules, file import/export, and local work. Its `No server` mode does not provide browser/PWA access, cross-device sync, or the server-backed API. See [Actual installation options](https://actualbudget.org/docs/install/).
- With a configured server, Actual keeps a local working copy and syncs it to the selected server; its official documentation describes offline operation and multi-device use. End-to-end encryption is optional, has a separate password, and has a password-loss recovery cost. The server administrator can access sync tokens, and local device data is not encrypted by Actual itself. See [syncing across devices](https://actualbudget.org/docs/getting-started/sync/).
- The server-backed UI proof uses the owner-authenticated local session. This establishes only the configured single-client state; it does not establish two-device sync or conflict behavior.
- Actual's official API is a Node package, not a REST service. With no `serverURL`, it makes no network connections and can use locally cached files; `runImport` can create a new local budget. Remote-server access requires its password. The documented browser build is experimental and requires cross-origin isolation. This gives a supported offline data-setup/export path, but does not replace UI interaction evidence for the 22 workflow scores. See [Using the API](https://actualbudget.org/docs/api/) and the [API reference](https://actualbudget.org/docs/api/reference/).
- Actual's user directory and per-budget user access require an OpenID Provider. This adds identity-provider setup and ongoing operations if separate household identities are required. See [Managing multi-user support](https://actualbudget.org/docs/config/multi-user/).
- **Interactive server-backed import checkpoint:** the local UI created one synthetic budget with six accounts and imported all six account-scoped CSVs (177 fixture transactions). Visible closing balances matched the fixture: Checking 11,330.11; Savings 11,000.00; Card Alpha 75.14; Card Beta -3,787.50; Auto Loan -15,950.00; Cash 624.00. Actual also created six opening-balance rows (183 ledger rows total). The sidebar showed **159 uncategorized transactions**. The budget initially had Actual's default categories but not the fixture's custom labels (Housing, Utilities, Insurance, Debt, etc.); the existing Income category matched, while unrecognized labels landed uncategorized. This shows category setup is a prerequisite for a clean UI import. The separate local API proof seeded the needed categories, preserving 123 fixture categories and leaving 54 transfer rows uncategorized. Duplicate re-import has not yet been tested in this server-backed budget. See [importing transactions](https://actualbudget.org/docs/transactions/importing/).
- **Schedule workflow checkpoint:** the schedule list initially had no entries. The UI created `SYNTHETIC Streambox monthly` for the existing Synthetic Streambox payee on Card Alpha, approximately $21.99, repeating monthly on the 11th from 2026-11-11. Automatic transaction creation remained off. The schedule then appeared as Scheduled with next date 11/11/2026. This proves a native schedule path; it does not yet prove schedule-to-ledger matching or price-drift explanation.
- The account view showed all six synthetic balances in the sidebar, with an all-account displayed total of 3,291.75. The browser viewport used for this capture was 1280×900; the earlier issue evidence separately covers phone-size/PWA layout.
- Actual supports user-initiated data export and desktop backup. The independent backup and fresh-client restore jobs remain untested. See [backing up Actual](https://actualbudget.org/docs/backup-restore/backup/).

## Gringotts evidence available so far

- The live local v134 app reports a local vault and a blank current dataset. Its restore preview accepted the 183-row synthetic fixture, but the first-run UI could not produce a current populated backup; its required acknowledgment and disabled confirmation prevent using the supported restore path from an empty destination.
- The v134 release contract describes local exports and explicitly records no network or persistent-store addition in the export executor. The app's current local-data model therefore does not itself provide cross-device sync.
- The deterministic fixture has 177 canonical transactions across six accounts, six Actual CSVs, Gringotts CSV and restore representations, expected outcomes, and a hash manifest. Manifest SHA-256: `bea0cbd3fb410a1b9c067f7f4e2e4f597f35a54523fca1fe099bfde5c9f2d536`.

## Decision limits

This evidence supports treating Actual's server-backed client as the serious cloud/offline baseline for #56, subject to a real second-client test. It does not establish household usability, conflict handling, replay behavior, interrupted-sync recovery, or spreadsheet exit quality. The interactive import requires category pre-creation for full category fidelity, so category setup effort must be included in the matched score. It does not justify building Gringotts sync. Final architecture/product scoring remains dependent on completing #54's matched 22-job execution.
